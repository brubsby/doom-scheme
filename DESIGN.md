# doom-scheme — design

A port of id Software's DOOM to Scheme.

**Target: linuxdoom-1.10** (`reference/doom/`), quirks and all. The C code is the
spec. **Chocolate Doom 3.1.1** (`reference/chocolate-doom/`) is the second
reference. It is a well-commented, actively maintained reading of the same
engine, and we consult it for:
- **What an obscure piece of C means**, plus the documented vanilla bugs.
- **Clean SDL2 platform code to crib from** (`i_video.c`, `i_sound.c`, `i_input.c`).
- **Edge cases that linuxdoom-1.10 leaves undefined.** Examples are reading past
  the end of a lump, or overflow behavior (`intercepts`, `spechit`,
  `visplanes`). When linuxdoom simply crashes or corrupts memory, we take
  Chocolate Doom's emulated behavior.

Where the two disagree on defined behavior, linuxdoom-1.10 wins.

## Goals

1. **Faithful to linuxdoom-1.10.** Same fixed-point math (its
   `double`-based `FixedDiv` provably equals integer division), same tables, same RNG, same tic order. The bar is
   that **the port's per-tic trace matches the headless linuxdoom-1.10 oracle
   bit-for-bit** while it plays the shareware demos (DEMO1–3 in `doom1.wad`). A
   demo records input only, so any divergence in the simulation shows up
   immediately. That gives us a free, strict end-to-end test.
2. **Readable against the C.** Every C module maps to one Scheme library with the
   same name, and every C function maps to a Scheme procedure with a predictable
   name (below). You should be able to open `p_map.c` and `src/p/map.sls` side by
   side and follow along.
3. **Plays at 35 Hz at 320×200 first.** Native-compiled Scheme should do this
   comfortably. A higher-resolution mode and an uncapped, interpolated framerate
   are planned for later (see *Future: hi-res and uncapped*). We don't build
   them now, but we avoid choices that would block them.

Out of scope for now: netplay (IPX/serial), the DOS sound drivers, and the
sound server process. We keep the `ticcmd_t` architecture because demos need it.

## Implementation: Chez Scheme 10 + SDL2

| Option | Why / why not |
|---|---|
| **Chez Scheme (chosen)** | Best native code of any Scheme; unboxed fixnum and flonum ops (`fx+`, `fxsra`, …); bytevectors for framebuffers and lumps; `foreign-procedure` makes SDL2 bindings a few dozen lines with no C glue. R6RS libraries give us real modules. |
| Guile 3 | JIT is decent, but the hot loops (column and span drawers) would be several times slower. |
| CHICKEN 5 | Compiles via C, which is fast enough, but it's a heavier toolchain and the FFI is less direct. |
| Racket CS | Built on Chez, but its runtime adds overhead and a larger surface area. |

The dev environment is a Nix flake (`flake.nix`) that provides `chez` and `SDL2`.

### Naming convention

`P_XYDist` → `p-xy-dist`, `R_RenderPlayerView` → `r-render-player-view`,
`mobj_t` → record `mobj`, field `momx` → accessor `mobj-momx` and mutator
`mobj-momx-set!`. Constants keep their C spelling in uppercase, e.g. `FRACUNIT`
and `MF_SOLID`. The C prefix tells you the module, and the module is named
after the C file it ports.

**Globals.** Doom shares many mutable globals between modules (`gametic`,
`usegamma`, `prndindex`, ...). R6RS forbids assigning an imported variable,
and Chez also refuses an exported macro that `set!`s a private one. So
`(define-global name init)` stores the value in a box and exports `name` as an
identifier macro. Any module can then write `name` and `(set! name v)` exactly
as in C, at the cost of one box indirection.

**Shared state.** C's globals are often defined in one .c file and used from
another, and the two .c files may need each other (p_setup calls
`P_SpawnMapThing` in p_mobj, which writes p_setup's `playerstarts`). R6RS
library imports must be acyclic. So a global declared `extern` in a header
lives in that header's library: `doomstat` (game state, players, starts),
`r_state` (level geometry), and `p_local` (blockmap, reject). Code then
imports the header, as the C does. Globals private to one file, like the
automap's `m_x` or `cheating`, stay plain `define`s in that file's library.

**Subsystems with cycles are one library.** The renderer's C files call each
other in cycles (r_bsp → r_segs → r_main → r_bsp; r_segs ↔ r_things), and
so do the playsim's (p_mobj → p_maputl → p_map → p_inter → p_mobj ...).
Both already share one header each (r_local.h, p_local.h). So `(doom
r_local)` and `(doom p_local)` are single libraries whose bodies `include`
one `.ss` file per C file. Inside them C's globals are plain variables;
the ones other modules read or set are define-globals (Chez refuses to
export a variable the library assigns). Types that both need, like
`mobj_t`, live in a library named after their header, `(doom p_mobj.h)`.
The dependency order is: data and platform libraries, then `r_data`,
`r_local`, `p_local`, then the front end. A C function that a lower library
calls stays in that library even if C puts it higher up. So far that is
`G_PlayerReborn`, `G_ExitLevel` and `G_SecretExitLevel` (g_game.c), which
the playsim calls; `gameaction` and `secretexit` moved to `doomstat` with
them. The one call upward that can't move, `P_KillMobj` closing the
automap, goes through `am-stop-hook`, which `am_map` sets when it loads.
`d_main`, `d_net` and `g_game` form the next cycle, and the front end
joins it (the menu starts games, the intermission and finale end them,
the status bar's idclev changes level), so `(doom d_main)` is the third
such library. Its define-globals are defined in `d_main.sls` itself, ahead
of the includes, since a define-global is a macro and must exist before
code that uses it expands. Two more calls go up through hooks:
`P_SpawnPlayer` wakes the status bar and heads-up text (`st-start-hook`,
`hu-start-hook`), and the automap tells the status bar when it opens and
closes (`st-responder-hook`); `d_main` sets all three when it loads.

**Structs.** `(define-struct name (parent) (field default) ...)` defines a
record with mutable fields, accessors `name-field` and mutators
`name-field-set!`. `(make-name)` returns a zeroed struct (defaults are
evaluated per instance), and `(make-name f ...)` sets the fields directly.
C's "struct begins with another struct" becomes a record parent:
`thinker` ⊃ `degenmobj` ⊃ `mobj`. That's why a sector's sound origin
(`degenmobj`) can be passed where C passes an `mobj_t*`. Pointers become
references (`#f` for NULL). Map records carry their array `index` for the
places where C subtracts pointers (`sec - sectors`). C enums are integer
constants (`GS_LEVEL`, `sk_medium`, `pw_allmap`), because C does arithmetic and
indexing with them and the trace prints them.

## Core representation choices

**Integers and wraparound.** Doom relies on 32-bit overflow in two places:
`angle_t` is an unsigned 32-bit value that wraps constantly, and some
`fixed_t` (signed 16.16) arithmetic overflows. Chez fixnums are 61-bit, so:
- Angles: every angle add or subtract goes through `angle+`/`angle-` (in
  `tables`, where `angle_t` lives), which apply `(fxand … #xFFFFFFFF)`.
- Fixed point: `fixed-mul` is `(int32 (ash (* a b) -16))`. The product of two
  int32 values can exceed fixnum range, so it uses generic `*`. We profile it
  before doing anything cleverer.
- `int32` gets applied wherever the C silently overflows. So does `c-abs`,
  because C's `abs(MININT)` stays `MININT`; `FixedDiv` depends on that. We find
  further places by diffing demo traces, not by guessing.

**FixedDiv.** linuxdoom-1.10's `FixedDiv2` computes
`(fixed_t)((double)a / (double)b * FRACUNIT)` (the integer version is `#if 0`'d
out). For int32 inputs this provably equals exact truncating integer division.
The numerator `a·2^16` is below 2^47 in magnitude, so a non-integer quotient
never comes within 2^-47 (relative) of an integer. A correctly rounded double,
or an x87 extended value, therefore can't round across one. We implement it
as exact `quotient`, which keeps it independent of FPU mode.
`tests/fixed.ss` confirms this on 300k cases against the oracle's own
`m_fixed.o`, including the `abs(MININT)` paths. One consequence: the
"linuxdoom vs. DOS v1.9 FixedDiv" difference doesn't exist.

**Structs → mutable records.** `mobj_t`, `player_t`, `sector_t`, `line_t`,
`seg_t`, and the others become `define-record-type` with mutable fields. Hot
render-side data (vertex coordinates, column offsets) may be kept in parallel
fxvectors instead, if profiling says so.

**Thinkers.** The C code keeps an intrusive doubly-linked list of
`{prev, next, function}`, where removal sets the function pointer to -1. We keep
a doubly-linked list of thinker records with a `func` field that holds a
procedure or `'removed`. Iteration order matters for sync, so we preserve the C
semantics exactly, including deferred removal.

**State table.** `info.c` holds 967 `state_t` entries whose action fields are
function pointers (`A_Chase`, `A_FirePistol`, …). `tools/infogen.py` emits the
function's name as a symbol, and the playsim resolves the symbols to its
procedures when it starts. An mobj's `state` field holds the state record
itself, as C holds a pointer, with `#f` for NULL. `mobjinfo[]` is
`mobjinfo-table`, because `mobjinfo` names the record type. Each state
record carries its own `index`, which stands in for C's `state - states`.

**Pointers into arrays.** Where C keeps a pointer into a byte array, the port
keeps the array and an offset. `R_GetColumn` returns `(values bytevector
offset)`; `dc_source` is two variables. Light tables (`lighttable_t*`) are
offsets into `colormaps`. The renderer's `short*` clip pointers
(`negonearray`, `screenheightarray`, `openings`, R_DrawSprite's `clipbot`
and `cliptop`) are offsets into one fxvector, `clipmem`, so
`ds->sprtopclip = lastopening - start` works unchanged. Arrays that C reuses
across frames without clearing (visplanes, drawsegs, the solid-seg list) are
allocated once, so stale fields carry over exactly as they do in C.

**Memory / zone.** `z_zone.c` is dropped and the GC replaces it. Purge tags
(`PU_LEVEL` and the like) go away, because level data is simply dropped on
reload. `W_CacheLumpNum` becomes a memoizing lump→bytevector cache.

**Framebuffers.** `screens[0..4]` are slices of one bytevector, `screens`,
starting at `(screen-base n)`. In C, screens 0–3 are carved contiguously out of
one allocation, and code relies on it: `G_DoSaveGame` writes the save buffer
at `screens[1]+0x4000` and can run into `screens[2]`. Pixels are palette
indices. The
platform layer converts to ARGB once per frame through a 256-entry palette
lookup and uploads to an SDL streaming texture. `I_SetPalette` passes each
component through `gammatable[usegamma]`, as linuxdoom does. Note that even
gamma 0 is not the identity: it maps 0..127 to 1..128. Palette flashes
(damage, pickup) are just a palette swap, as in the original.

**Endianness/parsing.** WAD lumps are read with `bytevector-s16-ref` and related
procedures using `(endianness little)`, so no `m_swap` is needed.

## Platform layer (SDL2 via Chez FFI)

- **Video:** a window with a 320×200 streaming texture, scaled with aspect
  correction (4:3).
- **Input:** SDL events become `event_t` (`ev_keydown`/`ev_keyup`/`ev_mouse`)
  and get fed to `D_PostEvent`. The key mapping comes from `i_video.c`'s
  `xlatekey`.
- **Timing:** `I_GetTime` returns tics at 35 Hz from `SDL_GetTicks`.
- **Sound:** SFX mixing is done in Scheme by a port of linuxdoom's sound
  server (11025 Hz, 16-bit stereo, 512-sample buffers). The mix is pushed
  with `SDL_QueueAudio` from the main thread, which avoids audio-thread
  callbacks into Scheme (see "Sound").
- **Music:** Chocolate Doom's OPL player and Nuked OPL3, in Scheme, on a
  second SDL device at 44100 Hz, also pushed from the main thread (see
  "Music").

## Verification: the C oracle

The design's centerpiece is a **headless reference build of the C code** in
`tools/oracle/`. It is linuxdoom-1.10 with the X11, sound, and network layers
stubbed out. Its simulation is left **unpatched**, so the oracle *is* the
target. The harness touches the original only in these ways:
- **Demo version check** (`tools/oracle/oracle.patch`). `G_DoPlayDemo` rejects
  demo version ≠ 110, but the shareware demos are version 109. The oracle
  accepts 109, and so does our port.
- **Trace hook** (same patch). `D_DoomLoop` calls `oracle_tic()` after
  `D_Display`.
- **Level dump hook** (same patch). `P_SetupLevel` calls
  `oracle_level_dump()` right after `P_GroupLines`, before things spawn and
  specials run. With `ORACLE_LEVELDUMP` set, it writes every vertex, sector,
  side, line, subsector, node, and seg (pointers as indices), plus hashes of
  the blockmap and reject lumps.
- **Built 32-bit** (`gcc -m32` via `$ORACLE_CC` from the flake). The 1993 code
  assumes 32-bit pointers, and this way nothing in the original changes.

`i_video.c` is replaced by a null layer. Rendering still happens into
`screens[0]`, the palette is captured, and `-devparm`'s tic-rate dots are
kept (they draw into `screens[0]` and call `I_GetTime`). Sound runs as
linuxdoom ships it: `doomdef.h` defines `SNDSERV`, so the game pipes its
sounds to a separate sound server (`reference/doom/sndserv`). The oracle
builds that server too (`build/oracle/sndserver`, `tools/oracle/sndserv.patch`),
patched to run in lockstep: the game's `I_SubmitSound` sends an extra "f"
command after each frame, and the server then mixes exactly one buffer and
writes its hash (`ORACLE_AUDIO`), instead of mixing whenever `/dev/dsp`
takes more. `ORACLE_SNDSERVER` names the server to run.

Whether the oracle itself stays in sync with the v1.9 recordings doesn't matter
to the gate. We only need to match the oracle. In practice the simulations
should be nearly identical.

Under `-timedemo`, which advances exactly one tic per frame, it writes one
trace line per tic. The exact format and hash definitions are documented in
`tools/oracle/oracle.c`:

```
gametic gamestate leveltime prndindex rndindex
px py pz pangle pmomx pmomy health armor
nmobjs mobjhash sectorhash framehash palettehash
```

It can also dump `screens[0]` as PPM every N tics, or as raw palette indices
after every frame (`ORACLE_RAW_DIR`, or only the frames in
`ORACLE_RAW_FRAMES`). `ORACLE_KEYS` posts scripted key presses after given
frames (`+k` holds a key down, `-k` lets go), which is how we drive the
oracle's automap and menus without a demo, and `ORACLE_EXIT` exits the
level after given frames (`G_ExitLevel` or `G_SecretExitLevel`, as an exit
switch would), for the intermission and finale. Run
`make oracle-traces` to get the traces. DEMO1, DEMO2, and DEMO3 run 5026, 3836,
and 2134 tics, in about 2 s each. The Scheme port emits the identical trace. `make sync-test` runs both on DEMO1–3 and reports the **first
divergent tic** and which field diverged. That turns "the demo desynced
somewhere" into "on tic 412, `rndindex` differs, so an extra `P_Random` call
happened". Renderer correctness gets the same treatment by comparing
framebuffers byte-for-byte on demo tics.

### Garbage reads

Vanilla occasionally renders from memory it doesn't own. The first case we
found is DEMO1, tic 606: a 1-pixel sprite column at the bottom edge of the view
(the shotgun psprite). There, `dc_texturemid + (dc_yl-centery)*dc_iscale` goes
negative, `(frac>>16)&127` wraps to texel 127, and the read lands past the end
of the sprite post. It lands in the zone allocator's block header, which holds
a byte of a heap pointer. As a result:
- **The oracle runs with ASLR off** (`setarch -R`, in `tools/oracle/run.sh`).
  With ASLR on, that pixel changes from run to run. With it off, traces are
  byte-identical across runs.
- **The port can't reproduce these pixels**, because they are bytes of C heap
  pointers. Reads past the end of a lump return 0 in the port. Chocolate
  Doom has the same behavior here, so there is no better-defined value to
  copy. Instead the port tracks them (below): a column drawer that reads
  past either end of its source marks that pixel in `garbage-mask`, and
  the fuzz drawer marks a pixel it copies from a marked one. Simulation
  fields are a hard gate; so is `framehash`, except on frames where every
  differing pixel is marked (`tests/frames.ss` checks the pixels).

- **Garbage reads are tracked, not allowlisted, where possible.** In
  low detail, linuxdoom's `R_DrawColumnLow` doubles the global `dc_x` on
  every post. Later posts of a sprite column then read the clip arrays
  outside the range they were filled for. In C those are `R_DrawSprite`'s
  uninitialized stack arrays, or whatever globals follow
  `negonearray`/`screenheightarray` in the binary. With `garbage-mask` set,
  the renderer marks the rows a sprite or masked seg could draw on whenever
  its clipping reads out of range. `tests/render.ss` then compares every
  other pixel. Of 252 test frames, only 5 low-detail frames hit this, and
  all high-detail frames are compared in full.

Out-of-range table reads (`finetangent`, `finesine`, `tantoangle`) raise an
error instead of reading neighboring memory, so a new case shows up rather
than silently differing.

Smaller layers get unit tests against values extracted from C: fixed math,
`R_PointToAngle`, and `P_AproxDistance`.

**Level and automap tests.** `tools/oracle/levels.sh` runs the oracle once per
shareware map (`-warp 1 n`). It writes the level dump, then types TAB+`iddt`,
`0`, and `g`, and saves the frame after each step. `tests/level.ss` prints
the same dump from `p_setup` and requires it to match line for line.
`tests/automap.ss` replays the keys into `am_map` and requires the automap
area to match byte for byte. The rows where hu_stuff draws text (the message
line and the level title) are left out until milestone 7.

**Renderer tests.** A camera probe (`oracle_camera_probe`, hooked at the end
of `P_SetupLevel`) renders the freshly loaded level, with things in their
spawn states, from a list of cameras. `tools/oracle/cameras.py` places 28
cameras per map on the spots of a spread of things. Each looks along the
thing's angle or a pseudo-random one, and the cameras cycle through the
smaller view sizes, low detail, extralight, and the invulnerability and
light-amp colormaps. `tests/render.ss` renders the same cameras, one process
per map as the oracle runs, and compares whole frames: 252 frames, all
pixel-exact apart from the tracked garbage reads above.

**Playsim tests.** `tests/sim.ss` plays demos through the port's `G_Ticker`
and compares each tic against the oracle's trace of the same demo. The
fields compared are gametic, gamestate, leveltime, `prndindex`, the
player's position, angle and momentum, health, armor, the mobj count and
hash, and the sector hash. The mobj hash covers every thing's position,
momentum, state, tics and flags; the sector hash covers every sector's
heights, light and special. (`rndindex`, `framehash` and `palettehash`
are compared by `tests/frames.ss`, which runs the whole game.) The demos
are:
- **DEMO1–3** from the IWAD: 5026, 3836 and 2134 tics, all in sync to the
  end.
- **Synthetic demos** from `tools/oracle/demos.py`, played by the oracle
  with `-timedemo`:
  - w demos: four per map, `-nomonsters`, 1400 tics of random walking,
    running, strafing and turning.
  - f demos: two per map, with monsters, 2100 tics, skills 1–5, fire held
    for some runs, use presses and weapon changes. They include deaths and
    the level reloads that follow, pickups, armor, and monsters fighting
    and dying.

All 57 demos match end to end: 99,196 tics. A deliberate one-character
mutation in `P_CheckMissileRange` makes DEMO1 diverge at tic 1112.

Functions the port doesn't have yet have stand-ins (`p_unported.inc.ss`).
These are now saving and loading, and screenshots (milestone 9). A
stand-in logs its first call, and a demo is compared only up to the tic
before that call. None of the current demos reach one.

**Game loop tests.** The oracle has two more switches: `ORACLE_FAKETIME`
makes `I_GetTime` return a counter that advances by one per call, so the
real-time loop (`TryRunTics`, `NetUpdate`) runs fast and the same every
time, and `ORACLE_MAX_GAMETIC` stops it. The port's `i-fake-time` does
the same, and `d-tic-hook` sees every gametic.
- `tests/loop.ss` runs the port's own `D_DoomMain` and `D_DoomLoop`.
  With no arguments, the title loop (title page, DEMO1, credits, DEMO2,
  HELP2, DEMO3, title...) matches the oracle's at each of its 2401
  frames, to gametic 12000. With `-timedemo demoN`, DEMO1–3 match on
  every tic and end with the same timing error.
- `tests/ticcmd.ss` checks `G_BuildTiccmd` against the oracle's
  (`probes/ticcmd_probe.c`) on 3000 tics of scripted keyboard, mouse and
  joystick input: accelerative turning, running, strafing, double clicks,
  weapon changes.
- `tests/record.ss` records a demo in the port (`-record`, 1500 tics of
  scripted key events, a pause, and q to end it), then plays it back in
  both the oracle and the port with `-timedemo`. Both playbacks match the
  recording run on every tic.

**Frame tests.** `tests/frames.ss` runs the whole game in both, headless,
with fake time, and compares every trace field of every frame:
`rndindex`, `framehash` and `palettehash` as well as the simulation. A
frame whose only difference is its `framehash` passes if every differing
pixel is marked as a garbage read: the test then has the oracle dump that
frame (`ORACLE_RAW_FRAMES`) and checks the pixels. The cases:
- `-timedemo demo1`-`demo3`: the status bar, messages, the palette
  flashes, the wipe into the level. 11,000 frames, 14 of them with
  garbage reads.
- The title loop to gametic 12000, with its wipes and pages (2401 frames).
- The menus, from the title loop: Read This!, every options item, the
  sound and load menus, the shareware episode message, the nightmare
  prompt, a new game.
- In a game: the automap with its title and cheats, the status bar cheats
  (god, ammo, the six powers and their palettes, mypos), messages, every
  screen size, help, pause, gamma, the save menu's text entry, the load
  and quit menus, idclev, and ending the game back to the title loop.
- The intermission, accelerated by fire and use, on into E1M2; the secret
  exit to E1M9 and back to E1M4, with the stats waiting and the map's
  "you are here" running out its delay; the end of the episode: the
  finale's text, the wipe to its picture, and the menu over it.
- Saving and loading (menus, quick save and quick load), and `-loadgame`
  from the oracle's savegames (see "Savegames").
- A `.doomrc` read and written back (see "The config file"), and
  `-devparm` screenshots.

With `make freedoom`, Freedoom's IWADs stand in for DOOM II and The
Ultimate DOOM (named `doom2.wad` and `doomu.wad`, so linuxdoom takes them
for those): their demos, DOOM II's title loop, intermission, text screen
and cast call, and episode 4's end. The oracle and the port only have to
agree, so Freedoom's data being different from id's doesn't matter. These
found three things the shareware cases never reached (see "Front end bugs,
kept on purpose"): the button sound's origin, The Ultimate DOOM's sky, and
the 180° angle reads.

Each side runs in its own directory with its own `HOME`
(`build/test/frames/NAME/{oracle,port}`). Every sound buffer the port's
server mixes must hash the same as the oracle's server's. All the frames
of the scripted cases match, and the scripts were checked by eye against
the oracle's frames (`VIEW=case` dumps them).

**Sound.** linuxdoom's game side (`s_sound`, `i_sound`) knows nothing
about what is playing: under `SNDSERV`, `I_StartSound` writes
`p<id><pitch><vol><sep>` to the server's pipe and returns the sfx id as the
handle, and `I_SoundIsPlaying` is `gametic < handle`. So after the first
hundred or so tics every `s_sound` channel is freed the frame after it
starts. `S_StartSound` calls `M_Random` for pitch variation, the same
stream the status bar face and the wipe read. The port keeps all of this.

The server (`sndserv.sls`) runs in-process. Its loop reads whatever
commands are waiting, then mixes one 512-sample buffer (eight channels,
pitch by a step table, volume and separation by lookup tables). The
original was paced by its blocking writes to `/dev/dsp`. Here, with an
audio device, `I_SubmitSound` runs loop iterations until about two buffers
are queued, as linuxdoom's two OSS fragments were; without one (tests), it
runs exactly one per frame, in lockstep with the oracle's server. On quit
(`I_ShutdownSound` sends "q") the server mixes until every channel is
done, and `I_WaitVBL` keeps the device fed meanwhile, as the separate
process did: the quit sound plays out.

linuxdoom's volumes are 0–15 out of the mixer's 0–127 (the `*8` in `S_Init`
and `M_SfxVol` is commented out), so a mix peaks at about an eighth of full
scale. The device gets it amplified by 4, clamped: an output level, after
the mix the tests compare. The server reads the IWAD itself; the port takes
the game's lumps, so a PWAD's sounds would be heard here and not there.

**Music.** linuxdoom has none: its music calls are dummies (the DOS
version's went to DMX, and the Linux one never got a music server). The
port plays music the way Chocolate Doom does by default, which is how DOS
Doom sounded on an OPL card: MUS converted to MIDI (`mus2mid`), parsed
(`midifile`), and played (`i_oplmusic`: the GENMIDI instrument bank, DMX
1.9's voice allocation, volume, pan and pitch bend) through Nuked OPL3
(`opl3`), driven by Chocolate's timer queue (`opl`), which runs the
player's callbacks at their sample positions while it generates. Both are
checked byte for byte against the C: `tests/opl.ss` runs register scripts
(melodic, rhythm, OPL3, buffered writes, random writes) through Nuked OPL3
and the port, and `tests/music.ss` renders songs through Chocolate's own
player (`probes/music_probe.c`, linking its `i_oplmusic.c`, `mus2mid.c`,
`midifile.c`, `opl.c`, `opl_queue.c`, `opl_sdl.c` and `opl3.c` with stubs
for SDL) and the port: every doom1.wad song, looping past the end, volume
changes, pause, song changes, both sample rates, OPL3 mode and the older
DMX driver behaviours. The menu's music volume (0–15) is the player's
volume divided by 8, as in Chocolate. `-nomusic` turns it off.

**Sound effects bugs, kept on purpose.**
- The chaingun is silent. Its sound is a link to the pistol's, and the
  server copies a link's length from `lengths[(link - S_sfx)/sizeof(sfxinfo_t)]`:
  the pointer difference is already an index, so that is `lengths[0]`, 0.
  It plays one sample.
- A missing sound lump (DOOM II's, in doom1.wad) gets an uninitialized
  length in C; here it is empty. Shareware never plays one.

**Savegames.** `p_saveg` copies whole structs into the savegame with
`memcpy`: `player_t`, `mobj_t` and the special thinkers, in their 32-bit
i386 layouts, pointers and padding included. The port describes each struct
as a list of fields with their C types, and computes the offsets from the
i386 alignment rules; `tests/saveg.ss` checks every offset and size against
the oracle's compiler (`probes/saveg_probe.c`). Pointers C doesn't swizzle
are written as 0, and on load C overwrites them all, except `mobj_t`'s
`tracer`, which keeps a stale pointer (only DOOM II's revenant and
arch-vile use it); here it becomes NULL. The savegame's description field
is 24 bytes of `savedescription[32]`, so the bytes after the terminator are
whatever earlier, longer descriptions left there, and the port keeps
`savedescription` as that buffer. The frame tests save, quick save, load
and quick load in a level with monsters, doors and lights in motion, and
start a game from the oracle's savegames with `-loadgame`. Every savegame
the port writes equals the oracle's except for the bytes C leaves undefined
(pointers, padding, and the bytes `PADSAVEP` skips; p_saveg records them in
`savemask`).

**Savegame bugs, kept on purpose.**
- Fire flickers (`T_FireFlicker`) aren't saved, so they stop after a load.
- Neither are plats in stasis: among thinkers with no function, only
  ceilings are looked for.
- A loaded thing's `floorz` and `ceilingz` are its sector's heights, not
  what they were.

**The config file.** `M_LoadDefaults` reads `$HOME/.doomrc` (or `-config
file`) with `fscanf (f, "%79s %[^\n]\n", ...)` and `sscanf`'s `%i`, and the
port reads it the same way: `010` is octal, `0x` hex, a name without a value
takes the next line as its value, a value that doesn't parse leaves the
previous line's number, and a string loses its first and last characters.
`I_Quit` writes the file back. The table includes linuxdoom's `sndserver`,
`mb_used`, `mousedev` and `mousetype`. A frame test starts from a `.doomrc`
with all of those cases, plays with the keys, screen size, detail, gamma
and sound it sets, and quits from the menu: both write the same file.

**Screenshots.** With `-devparm`, F1 writes `DOOMnn.pcx` (the PCX header's
`reserved` byte is uninitialized in C, and 0 here). The frame tests compare
the files.

**NetUpdate in the renderer.** `R_RenderPlayerView` calls `NetUpdate`
between its phases, so input can be read and commands built in the middle
of a frame. The port missed this at first; nothing in the traces showed it,
because the command buffer is full in steady state, but `-devparm`'s
tic-rate dots count `I_GetTime` calls and did. The renderer calls up to
`d_net` through `r-net-update`.

**Order of evaluation.** C leaves the order of `P_Random()-P_Random()`
unspecified. The oracle's gcc evaluates the left call first (checked in the
compiled `P_SpawnPuff`), as DOS Doom does, and `p-random-diff` follows
that. Function arguments that each call `P_Random` would need the same
check.

**Overflows and type puns that fail loudly.** `intercepts[128]` and
`spechit[8]` have no bounds checks in C, and overrunning them corrupts
neighboring memory. Both raise an error in the port instead.
`EV_VerticalDoor` writes a door's `direction` into whatever thinker the
sector has active, which could be a lift or floor. The port raises an
error unless it is really a door. None of these has happened in the tests
so far.

**Uninitialized fields.** C's `Z_Malloc` doesn't zero memory. A few
thinker fields are read without ever being set; the port reads them as 0.
These are `newspecial` for a `lowerAndChange` floor with no matching
neighbor, and a plat's `low` or `high` for some types. A demo that depended
on one would show up as a divergence.

**Known linuxdoom renderer bugs, kept on purpose.** Low detail is broken in
linuxdoom's C drawers, and the port matches it:
- `R_DrawSpanLow` doubles `ds_x1` and `ds_x2` before computing the count,
  so spans are drawn about twice as long. They run past the view window
  into the border and onto the next row.
- `R_DrawColumnLow` doubles the global `dc_x`, which the masked drawers'
  loops then continue from.
- `R_DrawFuzzColumn` doesn't double `dc_x` at all.

The DOS v1.9 executable drew with assembly routines that don't have these
bugs, so here the port matches linuxdoom (our target) rather than DOS.
Separately, `R_ClipSolidWallSegment`'s compaction loop copies one entry past
the old end of the clip list and keeps it, and the port does the same.

**Front end bugs, kept on purpose.** linuxdoom's front end has its own:
- `if (french)` tests the enum constant (always true), not the language.
  So `HU_Init` always takes the French shift table for chat, `HU_Responder`
  always translates chat keys through the French keymap, and
  `WI_loadData` picks "items" by netgame instead of language.
- `WI_drawAnimatedBack` tests `if (commercial)`, also always true, so the
  intermission map's animations are never drawn. They still run, and
  their `M_Random` calls still happen.
- `AM_Stop`'s `st_notify` initializer is `{ 0, ev_keyup, AM_MSGEXITED }`,
  so the status bar receives a keydown of 1 (which resets the cheat
  matchers) instead of "automap closed".
- `dstrings.c` misses two commas in `endmsg[]`, so two pairs of quit
  messages are joined.
- `M_Drawer`, after a line ending in `\n`, compares the line's length with
  the length of the rest of the message; when they're equal, the rest is
  printed in place of the line. It also copies lines into a 40-byte
  buffer: the joined quit message 8 is 51 characters before its first
  `\n`, which overflows it in C (the port just prints it; no test shows
  that message).
- idclev in DOOM II sets the episode to 0 and then rejects episodes below
  1, so it never works.
- `G_DoLoadLevel` picks DOOM II's sky by map number when `gamemode` is
  `commercial`, `pack_tnt` or `pack_plut`. The last two are mission
  values (2 and 3), equal to `commercial` and `retail`, so The Ultimate
  DOOM's levels get SKY1 (maps 1–9), not their episode's sky.
- `P_UpdateSpecials` plays a button's return sound from
  `(mobj_t *)&buttonlist[i].soundorg`, the address of the pointer field.
  The "mobj"'s x and y are then 12 and 16 bytes on: the next button's
  texture number and timer, a spot near the map's origin, usually out of
  earshot (and `S_StartSound` then draws no random pitch).
- Angles of exactly 180° are `INT_MIN` as an `int`: `R_ScaleFromGlobalAngle`
  then reads `finesine[-4096]`, and the seg loop `finetangent[4096]`,
  memory outside the tables. The port reads 0 and marks those columns (and
  floor and ceiling spans touching them) as garbage reads. Freedoom's DOOM
  II demos hit it.
- `M_Drawer` copies each line of a message into `char string[40]`. Quit
  message 8 (joined, as above) is 51 characters before its first `\n`:
  `strncpy` overflows the buffer and leaves it unterminated, so the line's
  width, and so where it is centered, comes from whatever follows on the
  stack. The port prints the 51 characters and marks the line's band as a
  garbage read.

## Uncapped framerate (`-uncapped`)

With `-uncapped` the main loop doesn't wait for the next tic: `TryRunTics`
runs whatever tics are ready (possibly none) and the frame is drawn
anyway, as often as the display allows (vsync). `r_interp` records, at the
start of every tic, where each thing is (x, y, z, angle), each sector's
floor and ceiling height, the player's view height and the weapon sprites'
offsets. Each frame then moves them to prev + frac·(cur − prev), where frac
is the time since the last tic in tics, draws (the view, the automap, the
status bar), and puts them back. Something with no record from the last tic
(just spawned, or a new level) is drawn where it is, and so is anything
that moved more than 64 units in one tic (a teleport). Timedemos show
each tic as it is. `tests/uncapped.ss` runs the title loop to gametic 4000
normally and uncapped (with time slowed down so that most frames see no
new tic): the simulation matches after every tic.

## Hi-res (`-hires k`)

`-hires 2` or `-hires 4` renders the 3D view at k times 320×200 (640×400 or
1280×800); everything 2D stays 320×200. Like `-uncapped`, it is a display
option: the default is the original resolution, which the oracle tests
check, and `tests/display.ss` runs the title loop with each option (and
both together) and requires the simulation to match the plain run on every
tic.

- **The renderer has its own resolution.** `rwidth` and `rheight` are its
  width and height and `rbuf` its buffer. At k = 1 `rbuf` is `screens`, and
  everything is as before. View sizes are the 320×200 ones times k
  (so the view window, the status bar's height and the border stay aligned
  to the 2D layer), and `view2d-x` and friends give the window in 320×200
  for the 2D code that needs it (the border, the heads-up erase, the pause
  sign).
- **Scales grow by k, and three things follow.** The light-by-distance
  index for walls and sprites shifts by log2 k more, the light table takes
  the view's width at 320×200, and the cap on a wall's scale (64) grows by
  k too. The zlight table (floors and ceilings) depends on distance only and
  needs nothing.
- **Visplane columns are 16 bits.** C's are bytes, with 0xff for an empty
  column; at k = 1 they still wrap to a byte and use 0xff, and above it they
  are 16 bits with 0xffff.
- **The 2D layer composes on top.** After rendering, the view is
  downscaled into screen 0, so screen 0 is always the whole picture at
  320×200 (the wipe and screenshots read it), and an overlay mask is cleared
  over the view window; `v_video`'s drawing into screen 0 marks the mask.
  `I_FinishUpdate` then shows screen 0 scaled up k times, except that inside
  the view window, wherever the mask is clear, the pixel comes from the hi-res
  view. So the menu, messages and the pause sign sit on top of the view as
  they do in 320×200, and the automap and the wipes are 320×200.
- **linuxdoom's bugs come along.** `M_ChangeDetail` says low detail is "n.a."
  but flips `detailLevel` anyway, and the next resize applies it, with
  `R_DrawSpanLow` drawing spans twice as long: on the bottom row they run
  past the picture. In C they run into screen 1, so `rbuf` has a second
  screen's worth of room too.

DEMO1 (`-timedemo`, no display) renders at about 1300 frames a second at
320×200, 270 at 640×400 and 90 at 1280×800 on the development machine.
